# M2.6.80 — Build identity, engine-change save protection and the first flexible-base probe

Regular app 0.2.80 / 2680. The Mod Test app derives 0.2.80.1 / 268001. The engine remains OpenCE build 125 (`13c14df`), network version 16, with the 20 MiB game state used since M2.6.76. M2.6.79 passed the maintainer's GitHub Actions build; M2.6.80 itself still needs its Apple build and device checks.

## What changed

- **Every IPA now identifies the exact engine it contains.** The app bundle carries the Halo CE iOS milestone, OpenCE release and commit, network version, game-state size, guest ABI/architecture/adaptation, renderer, build flavor, diagnostic mode, GitHub source commit/run and SHA-256 of the bundled `halo_guest.elf`. Actions stamps the fields after the guest is bundled and before the app is signed. Settings → Advanced → About shows the concise identity and guest-hash prefix; engine boot logs and Share/Copy logs include the full OpenCE commit and full guest SHA-256.
- **Engine changes protect saves automatically with the existing `.halobackup` format.** On the first M2.6.80 start the app records the current engine identity without creating an unnecessary archive. On a later start, if the stable OpenCE/save-compatibility identity changes and persistent saves or Halo profiles exist, the app creates a verified saves/profiles `.halobackup` before the guest can open them. If that backup cannot be completed, Halo does not start. The identity uses OpenCE release/commit, network/game-state ABI and the explicit iOS guest architecture/adaptation; the exact guest SHA remains build metadata rather than a backup trigger because the guest embeds a compile timestamp. The last automatic archive can be exported from Manage backups. Normal manual backups and restore recovery are unchanged.
- **Backups now record engine identity in their manifest.** Format 1 stays compatible; older readers ignore the additional manifest fields and current restore code continues to accept older archives.
- **Reusable upstream-update acceptance gates.** `python3 tools/ios_upstream_acceptance.py` checks build metadata against `upstream.json` and the source network/game-state constants, rejects real merge-conflict markers, and runs the iOS guard-structure, host-import, workflow, declaration and checkpoint gates. A PC updater can pass `--upstream-root <exact OpenCE tree> --require-upstream` to compare every upstream-owned `HALO_IOS_GUEST`-adapted file against that exact candidate. The M2.6.79/build-125 baseline has 27 pre-existing flags-off divergences; their hashes are recorded in `upstream_baseline_deltas.json` as explicit transition debt, not silently treated as upstream. `--require-clean-flags-off` is the promotion gate for a new OpenCE integration: it rejects even those grandfathered build-125 deltas and requires zero differences. `--json` writes a machine-readable result for an updater UI. GitHub Actions runs the local gates on every IPA candidate.
- **Non-Jailbreak Stage 1: exact 4 GiB anywhere.** When the production 8 GiB reservation fails, the Non-Jailbreak report now makes and releases one explicit 4 GiB reservation at any address and records the actual base, whether it happened to be 4-GiB aligned, and its offset within a 4 GiB block. This is diagnostic only. M2.6.80 still requires the existing aligned arena to execute Halo, so Regular, Mod Test and the real guest pointer contract are unchanged.

## Why the Non-Jailbreak probe is separate

The tested free-signed iPhone 14 Plus could reserve 4 GiB but could not obtain a usable 4-GiB-aligned guest window. M2.6.80 is designed to confirm that distinction cleanly on the actual install before the project starts converting the real guest to an arbitrary-base pointer model. A log such as `Flexible 4 GiB ANYWHERE: SUCCESS ... 4 GiB-aligned: NO` is therefore a useful result even though this milestone will still stop at `STARTUP BLOCKED: ADDRESS SPACE` afterward.

No signed/static guest-code redesign is included here, and ANGLE/Metal is not introduced. Rendering remains Apple OpenGL ES.

## Validation in this source tree

- The M2.6.79 GitHub Actions build was reported green by the maintainer and is the baseline for this update.
- The backup regression now covers first identity adoption, an engine-identity change, creation of the automatic `.halobackup`, preservation of the previous engine identity in the archive manifest, and no duplicate backup when the identity is unchanged.
- The address-space planner regression covers an unaligned-but-usable 4 GiB span and verifies the report says `4 GiB-aligned: NO` without leaking the reservation.
- The build-identity regression checks M2.6.80 versioning and consistency with OpenCE build 125, network version 16 and the 20 MiB source game-state constants.
- The upstream acceptance runner passes all local gates. A direct audit against OpenCE build 125 commit `13c14df95c63156429e96a9694bb9cecd0379228` checked 43 upstream-owned adapted files: 16 are exact with iOS blocks removed and 27 match the fingerprinted M2.6.79 legacy-delta baseline. Two iOS-owned helper headers have no upstream counterpart and are excluded from this particular equality gate. Strict promotion mode intentionally rejects those 27 deltas until a future integration cleans them up.
- The Linux/local regression sweep passes 32 of 33 `test_ios_*.py` files. The only one that cannot start here is `test_ios_pointer_fastpath.py` because this workspace does not have the `keystone` module; GitHub Actions creates a venv and installs `unicorn==2.1.4` and `keystone-engine==0.9.2` before running it.
- The complete `ios-memory-tests` C/host diagnostic sequence passes locally, as do the remaining main-workflow C preflight tests for controls, faults, logs, SDL events, audio ring, networking, texture hashing, launch state, frame pacing, vertex handling and render/scene scans. The XISO suite passes 9/9 with GCC and 9/9 with Clang.
- Apple/Foundation-specific compilation and the updated `.halobackup` Objective-C regression still require the M2.6.80 GitHub Actions run; no device result is claimed here.

## Device checklist

1. Build the regular app. Confirm About shows **M2.6.80**, **OpenCE build-125 / 13c14df…**, **network 16**, Regular, aligned-arena-v1, ios-guarded-v1, Apple OpenGL ES and a guest-SHA prefix; confirm Share logs contains the full OpenCE commit and full guest SHA-256.
2. Start with existing M2.6.79 saves. The first M2.6.80 start should establish the engine identity without creating an engine-change backup because the engine is still build 125. Confirm normal campaign save/load and profile persistence.
3. For a later test build with a deliberately changed test engine identity, confirm Halo creates an automatic `.halobackup` before the game starts and that **Manage backups → Export last engine-change backup** exports it. A forced backup failure must block startup rather than expose the saves to the changed engine.
4. Build **Non-Jailbreak Version**, sign it the same free-account/Sideloadly way used for the earlier iPhone 14 Plus test, and share the full log. Record the new `Flexible 4 GiB ANYWHERE` line, actual base, `4 GiB-aligned` answer, existing aligned-window results and executable-memory result.
5. Build Mod Test manually and confirm it reports **0.2.80.1 / 268001**, its build flavor is ModTest, and its separate bundle/data behavior is unchanged.
